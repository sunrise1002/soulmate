Soulmate

An open-source, local-first personal AI system whose goal is not to be the smartest general agent, but to understand one specific person as accurately as possible — and to keep that understanding on that person's own machine.

Local-first Self-hosted Python 3.12 · TypeScript · Rust Apache-2.0 Phase 12 complete locally

1. Overview #

Soulmate builds a Personal Decision Model: a versioned, inspectable model of what its owner prefers, values, aims for, and is constrained by. It answers questions such as “What would I probably choose?”, “Knowing my long-term goals, what should I choose?”, and “If another AI had to decide for me, what would I want it to do?”

There is no Soulmate cloud. Every user runs their own service; the database, the embeddings, and the model live in a directory the user controls. LLM providers, clients, and external agents are replaceable parts around that core.

Owner-controlled data

SQLite plus local files on the owner's machine. No telemetry, loopback-only by default.

Explainable beliefs

Every belief traces back to the evidence and the raw event that produced it, and can be corrected or deleted.

Deterministic core

Prediction, learning, and policy decisions are local and deterministic. LLMs propose; they never mutate the model.

Replaceable everything

Ollama, OpenAI-compatible endpoints, desktop/web/mobile clients, MCP agents, and connectors all plug into stable ports.

2. Vision & goals #

The system continuously learns, from evidence rather than assertions:

  • what the owner likes and dislikes, and what they value;
  • their goals, constraints, and behavioral patterns;
  • how they weigh trade-offs, and how that changes with context;
  • which decisions they actually made, and whether they were satisfied afterwards;
  • how confident the system should be about each individual belief.

Product philosophy

PrincipleWhat it means in practice
Local first All persistent personal data lives on infrastructure the owner controls: daemon, SQLite, embeddings, attachments, Personal Model, keys.
Self-hosted Runs on Mac, Windows, Linux, a home server, a NAS, or a personal VPS. The non-technical path is “install desktop app → it starts its own daemon”.
Agent ≠ Personal Model The Personalization Kernel is independent of any agent runtime, web framework, or model vendor. Conversation is an input channel, not the model.
Evidence over assertion Nothing is stored as a bare fact. Claims are stored as evidence with provenance, strength, and confidence; the model is derived and rebuildable.
Explicit consent Network access, other devices, external agents, and connectors are all off until the owner turns each one on, one scope at a time.

3. Non-goals #

Knowing what this project refuses to become is as important as its goals. Soulmate is not:

Not a product shape

  • a SaaS personalization platform;
  • a multi-tenant cloud product;
  • a cloud synchronization service;
  • a general knowledge assistant;
  • a general autonomous agent framework.

Not an infrastructure shape

  • no Kafka, Kubernetes, Redis cluster;
  • no Neo4j, Elasticsearch, dedicated vector DB;
  • no microservices, no distributed system;
  • nothing sized for millions of centralized users.
Rule of thumb.

New infrastructure is only justified by a clear local use case. Remote internet exposure is explicitly out of scope — use a VPN if you need access away from home.

4. Core concepts #

4.1 The evidence pipeline

Conversation history is not the Personal Model. Everything flows one way, and derived state can always be thrown away and rebuilt:

RawEventImmutable captured input: a message, an import, a connector item, a recorded choice.
→
EvidenceA provenance-bearing claim: target, value, strength, confidence, context, extractor version.
→
Derived modelPreferences, facts, goals, constraints aggregated from all evidence.
→
SnapshotA versioned UserModelSnapshot. Every prediction records the snapshot it used.

Instead of storing a conclusion such as {"likes_subscription": false}, the system stores the claim that produced it:

{
  "target_type": "preference",
  "target_key": "payment.subscription",
  "value": -0.6,
  "strength": 0.7,
  "confidence": 0.72,
  "context": { "domain": "software" },
  "source_type": "explicit_statement",
  "source_event_id": "evt_...",
  "extractor_version": "preference-extractor-v1"
}

Contradicting evidence is preserved, not overwritten. The aggregate may conclude “subscriptions: negative overall, neutral-to-positive for developer tools when the productivity gain is high”. Because the chain is intact, the owner can ask why the system believes something and get the supporting evidence back — and deleting a source deletes its evidence and rebuilds the model.

4.2 Evidence reliability

Not all evidence is equal. Weighting is configurable and versioned rather than hardcoded as truth:

SourceWeightSourceWeight
Casual inferencelowActual decisionhigh
Explicit statementmediumRepeated actual decisionsvery high
Hypothetical scenariomediumUser correctionvery high
Pairwise calibrationmedium/highOutcome / regret feedbackvery high

4.3 Two decision modes, never merged

Predict Me — descriptive

“What would I choose?” Models actual behavior: P(choice | user, context). Local, deterministic scoring combining global, domain, and matching-context preferences with online pairwise learning from prior resolutions.

Advise Me — normative

“Knowing me, what should I choose?” Independently combines the prediction with satisfaction and regret history, similar resolved decisions, and matching goals or constraints.

Why separate?

It is valid — and useful — for the system to say “I predict you would choose A, but based on your stated long-term goal I recommend B.” Both results report their model snapshot and algorithm version, and clients display them as two distinct answers.

4.4 The role of the LLM

A model provider is a text interface, not an authority. It can propose structured evidence from a conversation; proposals are schema-validated by the daemon and pass a review policy before acceptance. A provider can never mutate derived Personal Model state, and only lexically relevant context is compiled and sent — never the whole database.

5. Architecture #

Soulmate is a local-first modular monolith with hexagonal (ports and adapters) boundaries. All dependencies point inward; the innermost layer knows nothing about HTTP, UI, storage engines, or vendors.

Clients
Tauri desktop shell · React web client · Expo mobile client · MCP-capable external agents
↓ REST over loopback / TLS · stdio MCP
Daemon composition root & adapters
FastAPI routes · single authorization boundary · prompts & proposal validation · durable job worker · SQLite adapter · provider adapters · egress policy · TLS & pairing · archives & imports · connector host
↓ application services and ports
Personalization Kernel (infrastructure-independent)
Memory · Evidence · User Model · Preference Learner · Decision Predictor · Advisor · Context Compiler · Active Learning · Evaluation · Policy Engine · Pairing & access rules
↓ driven ports
Infrastructure
SQLite + Alembic migrations · local object/index/model files · model APIs (Ollama, OpenAI-compatible) · OS credential store

The kernel must not import FastAPI, MCP, any UI, any vendor SDK, or any agent framework — and it does not import the connector SDK or any plugin either. That constraint is what makes the model portable across every replaceable part above it.

8. Setup #

8.1 Path A — desktop application (recommended for owners)

The installed application starts and supervises its own loopback daemon, stores data in the platform application-data directory, and requires no separately installed Python, Node.js, database, or Docker runtime. 

# build a native installer plus its bundled daemon sidecar
pnpm --filter @soulmate/desktop tauri build

8.2 Path B — run the service directly

uv run --locked decision-twin serve

The process listens on 127.0.0.1:7432, applies packaged Alembic migrations, creates DATA_DIR/decision-twin.db, and starts the durable local job worker. Stop it with Ctrl+C. It enables no telemetry, and model calls happen only when /v1/chat is used and the configured egress policy allows them.

8.3 Path C — development environment

Install uv, Node.js 24, pnpm 11.21.0, and Rust 1.88+. uv manages the Python 3.12 interpreter. 

# if uv lives in ~/.local/bin and your shell cannot find it
export PATH="$HOME/.local/bin:$PATH"

uv sync --locked --all-packages
pnpm install --frozen-lockfile
uv run --locked pre-commit install

pnpm check                                   # lint, format, typecheck, test — everything
rustup component add rustfmt clippy
pnpm --filter @soulmate/desktop tauri dev    # desktop product in dev mode
PATH matters for hooks.

Your editor's Git environment also needs uv on PATH, otherwise the pre-commit hook fails when committing from the editor.

8.4 First run checklist

  1. Copy config.example.toml to config.toml (optional; local config is git-ignored).
  2. Point the provider at a local model, e.g. SOULMATE_LLM__OLLAMA__MODEL=llama3.2. The daemon starts fine without one; /v1/chat simply reports the provider as unavailable.
  3. Run decision-twin doctor — it checks storage permissions, database integrity, WAL, foreign keys, migration state, port availability, and whether the selected provider has a model.
  4. Start chatting and deciding. Optionally import existing history with decision-twin import ./history.json.

9.3 Evaluation

evaluate is the project's honesty check. It reports accuracy, Top-2 accuracy, log loss, multiclass Brier score, and confidence-calibration error for five comparable systems: random, a frozen LLM-only baseline, memory-only, the Personal Model, and the full Decision Model. Run it against your own dataset with the same validated schema via --dataset.

10. Configuration #

Configuration belongs to the daemon: standard-library TOML parsing plus Pydantic v2 validation. Loading settings alone creates no files and calls no providers.

Precedence, lowest to highest

  1. Typed defaults.
  2. TOML file: serve --config PATH, else SOULMATE_CONFIG_FILE, else ./config.toml.
  3. DATA_DIR, which overrides TOML data_dir.
  4. SOULMATE_* environment variables, using __ for nested fields.

An explicitly selected config file must exist; a missing implicit ./config.toml just uses defaults. Invalid TOML, unknown keys, and unreadable files fail loudly. .env files are not loaded automatically.

Privacy modes

strict_local — default

All data, embeddings, and inference stay local. Model requests are restricted to literal loopback endpoints.

hybrid

External HTTPS providers allowed; plaintext external HTTP never is. Only minimal compiled context leaves the machine, and the UI indicates when it will.

offline

No network access at all, including for connectors. Local inference only.

The egress policy is central: it is enforced inside both HTTP adapters immediately before every request, so no component can quietly make its own calls.

Full details, including desktop settings storage and connector credential variables, live in the configuration reference.

12. External agents & MCP #

Other AI systems can consult the Personal Model without ever reading it. An external application uses a separate service-identity boundary even on loopback; it never inherits owner authority.

12.1 Scopes

Least privilege is enforced per identity. Implemented scopes:

ScopeGrants
model:summary:readDerived model summary.
preference:summary:readDerived preference summary.
decision:predictPredict a choice, rank options, find similar decisions.
decision:recordRecord a decision.
outcome:recordRecord an outcome.
agent:delegateRequest, read, and complete prediction-bound delegated actions.

Each identity carries one or more independently revocable high-entropy API keys. Only SHA-256 hashes are stored, the usable key is shown exactly once, and scope or revocation changes take effect on the next request.

12.2 MCP adapter

SOULMATE_API_KEY='<key-shown-once>' uv run --locked decision-twin mcp

Set SOULMATE_BASE_URL only when the daemon is not on the default http://127.0.0.1:7432. Nine tools are exposed:

predict_choice        rank_options            get_preference_summary
find_similar_decisions  record_decision       record_outcome
request_delegation    get_delegation          complete_delegation

Example MCP client configuration:

{
  "command": "uv",
  "args": ["run", "decision-twin", "mcp"],
  "env": {
    "SOULMATE_BASE_URL": "http://127.0.0.1:7432",
    "SOULMATE_API_KEY": "<key-shown-once>"
  }
}

The adapter is a REST consumer: it never opens the SQLite database and passes exactly the same authorization boundary and application services as HTTP callers.

12.3 Delegated decisions

A deterministic Policy Engine — part of the kernel, not the agent — decides whether an external action may proceed. The owner grants agent:delegate and creates a policy for one exact action type, assigning an impact level and a confidence threshold. Impact is never accepted from the agent.

ImpactAutomatic approval requires
Lowconfidence ≥ 0.90
Mediumconfidence ≥ 0.95
High / safety-criticalnever automatic — always owner confirmation

Every request binds to the latest persisted prediction from the current model snapshot, carries a per-agent idempotency key, expires after 24 hours, and survives restart. Soulmate returns authority and the predicted option — it never performs the external side effect itself.

13. Connectors #

Connectors bring outside data in without adding dependencies to the kernel. They are installed as separate Python packages and discovered through entry points.

InstallA separate Python package declaring a connector entry point.
→
ReviewThe Connections screen shows the manifest's declared data, network, credential, and learning permissions.
→
RegisterGrants must match the declaration exactly. Credentials come only from process variables.
→
SyncA durable local job deduplicates external item identities and writes source-linked RawEvents.
  • Credentials are read only from DECISION_TWIN_CONNECTOR__<CONNECTOR_ID>__<KEY> — never accepted by the API, persisted, logged, or included in archives.
  • Network-capable plugins get a host-allowlisted HTTP client behind the central privacy policy; offline mode denies all connector network calls.
  • Jobs persist only sanitized status and audit metadata.
  • Removing a connector deletes its RawEvents and derivative Evidence, then rebuilds the model.
  • The bundled Local Notes reference connector reads only UTF-8 Markdown and text files under one configured directory, and makes no network calls.
Trust boundary.

Installed Python plugins execute as trusted owner-selected code, not inside a security sandbox. Read ADR-012 before installing a third-party connector.

14. Data portability #

Import

UTF-8 generic JSON, Markdown, plain text, ChatGPT exports, and Claude exports. Creates provenance-linked conversations and RawEvents locally, with no hidden provider egress.

Backup — .dtwb

Credential-free local archive using SQLite's online backup, so committed WAL data is captured. Defaults to DATA_DIR/backups.

Export — .dtw

Portable archive with scrypt key derivation and AES-256-GCM authenticated encryption. Prompts for a passphrase, or reads --passphrase-file.

Restore

Validates paths, checksums, and versions; refuses non-fresh installations; migrates known schemas forward; issues a new installation identity; rebuilds the model from Evidence.

Archives include the database and any local objects, indexes, and models files. They exclude pairing state, API credentials, installation identity, TLS keys, provider secrets, logs, configuration, and existing backups.

# restore only while the daemon is stopped, and only into a fresh installation
DATA_DIR=./fresh-data uv run --locked decision-twin restore ./backup.dtwb
DATA_DIR=./fresh-data uv run --locked decision-twin restore ./personal-model.dtw
Restore never merges.

It will not overwrite or blend into owner-created data. Deleting an imported source removes its messages, RawEvents, and derivative Evidence before the model is rebuilt.

15. Privacy & security #

BoundaryGuarantee
NetworkLoopback by default, no telemetry. LAN access is off until enabled; when on, the loopback listener stays and one explicit TLS address is added. Wildcard binds are rejected by both configuration and resolver.
Pairing256-bit single-use tokens, five-minute expiry, claimed atomically so a token can never be redeemed twice. Only hashes of tokens and device credentials are stored; failed auth returns one generic message; revocation applies on the next request.
TransportSelf-signed certificate with an owner-only private key, renewed near expiry or on address change. The QR payload carries the fingerprint so a phone pins the exact service it paired with.
External identitiesSeparate boundary even on loopback; explicit scopes; SHA-256-hashed keys; responses omit raw memories, evidence, outcome history, and notes.
AuditLocal, metadata-only: identity, credential id, method, path, status. Never the key, never the payload. Pairing issue, device pairing, and revocation are audited.
SecretsProvider secrets come from the environment or the OS credential store — never TOML, never archives. The desktop UI only learns whether a key exists.
EgressOne central policy enforced inside both HTTP adapters immediately before every request — for model calls and connector calls alike.
ErrorsConfiguration errors name the offending field without printing its rejected value.
Known limits.

Browsers warn on the self-signed certificate until the owner accepts it. There is no per-address rate limit on pairing attempts. Connector plugins are not sandboxed. Remote internet exposure is unsupported by design.

Never put personal data or secrets into issues, logs, fixtures, source control, or CI artifacts. Use synthetic fixtures; keep runtime data out of tracked source. See privacy and security boundaries and SECURITY.md.

17. Status & limitations #

Phase 12 complete locally Phases 0–12 are implemented and verified locally on macOS arm64. No later product phase is defined or authorized — do not infer a Phase 13. Any further autonomous execution, notifications, policy language, or safety-critical behavior needs newly specified, explicitly authorized scope.

Honest unknowns

  • Remote CI has never been confirmed green; local checks are not a substitute.
  • Cross-platform installers, code signing, and packaged connector discovery are unverified outside macOS arm64.
  • Native mobile builds and browser trust of the self-signed certificate are unverified.
  • Confidence calibration against broad real-world data, and external action verification, remain open.
  • Vector search and vector diagnostics are deliberately deferred; the Python SDK is a documented placeholder; Docker packaging is a placeholder.
  • Connector plugin sandboxing/signing and scheduled syncs are not implemented.

The authoritative, always-current version of this list is docs/phase-status.md plus the individual phase reports.
